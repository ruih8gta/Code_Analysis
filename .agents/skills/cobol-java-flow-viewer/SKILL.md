# COBOL・Javaの移行レビュー

目的は、移行前の処理が移行後も保たれるか、何が違うかを根拠付きで確認できるようにすること。ビューアーはそのための道具である。工程の目的、成果物、確認状態を全体像に示し、同じ画面へすべての情報を重ねない。

## 工程を選ぶ

依頼に必要な工程だけを読み、既存成果物を引き継ぐ。

1. [現行仕様の可視化](../legacy-spec-visualization/SKILL.md)：原本とフロー、処理・分岐の網羅を確認する。
2. [新旧の処理比較](../migration-behavior-review/SKILL.md)：旧新の処理を対応付け、差分と検証根拠を確認する。
3. [データ項目の対応](../migration-data-mapping/SKILL.md)：変数・ファイル・DB項目の型、意味、変換、未整理箇所を確認する。

これは単純な完了順ではない。項目の問題から処理比較へ、比較の疑問から現行仕様へ戻れるようにする。前工程の未確認事項は後工程へ引き継ぎ、依存しない作業を進める。

## 原本の取得・Java移植を含む場合

- 対象ファイルと固定版、取得元、ハッシュ、ライセンスを保存する。1本の移植対象とCOPY句等の依存を区別する。
- コメントだけで役割を決めず、実際の制御フロー、入出力、更新、異常終了を確認する。
- Javaでは対象の順序、分岐、出力、更新、終了を対応付ける。VSAMをMap／Setへ置き換える場合は、読込時点、キー、重複、排他、文字コード、例外処理の差を記録する。
- 原本の特殊な動作や不具合の候補を黙って修正しない。変更する場合は理由・影響と採否を残す。
- 既存の新実装のレビューだけなら、それを比較対象として扱い、依頼されていない実装変更を混ぜない。

## 共通成果物と画面

版・根拠・処理ID・項目ID・差分・証拠を[レビュー契約](references/review-contract.md)でつなぐ。全体像には各工程の問い、現在の対象範囲、未確認事項、次の確認を表示する。

実装するときは[ビューアー実装メモ](references/viewer-implementation.md)を読む。[動作例](assets/carddemo/viewer.html)はソースとレビュー台帳を内蔵したCardDemoの単独HTMLであり、一般的なCOBOL解析器ではない。別対象ではコード、定義、対応、ケース、証拠を再構成する。

ローカル成果物を基本に、原本と移植版、対応台帳、実行結果、未確認事項をプロジェクト内に保存する。サンプルの見やすさと移行の妥当性を同じ完了条件にしない。実行可能な検証を行い、画面の主要操作とソース位置を確認してから、使えるデモと保存先を渡す。
