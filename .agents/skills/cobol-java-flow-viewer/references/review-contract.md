# 工程間のレビュー契約

同じ処理・データ項目を、現行仕様、新旧比較、項目対応の間で辿るための契約。形式はJSON、表、DB等に合わせられるが、次の意味を保持する。

## 共通の識別と根拠

| 対象 | 持たせる情報 |
|---|---|
| レビュー対象 | 旧／新のファイル一覧、版／ハッシュ、文字コード、依存、対象範囲と未取得資料 |
| 処理 | 安定した処理ID、入口・出口、条件と後続、呼出し・復帰、旧ソース根拠 |
| 処理対応 | 対応ID、旧処理ID、新の処理単位、両側の根拠、対応の多重度、差分、関連項目ID |
| データ項目 | 修飾した項目ID、種別、旧／新の定義、利用箇所、型・桁・制約、変換、関連処理ID |
| 差分 | 差分ID、説明、観測または推論の別、影響、前提、次の確認、採否とその根拠 |
| 実行証拠 | 証拠ID、ソース・依存・入力の版、環境、実行日時、比較対象、期待値の由来、実際の観測と判定 |

ソース根拠にはファイル、版、1始まり・末尾を含む行範囲を持たせる。行番号だけで版をまたいで再利用しない。名前が同じ項目やFILLERは、レコード・スコープ・位置で区別する。対象が分割・統合されてもIDと対応の履歴を辿れるようにする。

## 独立させる状態

1. **構造の対応**：登録、一部、未登録、未解析、理由付き対象外。
2. **意味上の比較**：対応あり、変更、追加、欠落、判断保留。判定の根拠を併記する。
3. **実行証拠**：未実施、モデル期待値対新実装、新旧実行の直接比較、境界・異常系確認など。対象と結果は別フィールドにする。
4. **採否**：未判定、許容する変更、要修正等。実際に決定されたときだけ判断者・日時・理由を記録する。

緑の行範囲、モデルで通過した図の辺、テストの成功は別の事実。一つの百分率へ混ぜない。分母は対象ソースから棚卸しし、未解析・未取得や理由付き除外も見えるようにする。

## 変更・古い証拠

旧新ソース、依存定義、入力、解析・比較モデル、正規化規則が変わったら、影響を受ける対応と証拠を古い状態にする。再実行・再レビュー前に成功表示を引き継がない。単独HTMLは保存時点のスナップショットで、外部ファイルの最新状態を自動取得しているとは表示しない。

## このプロジェクトの具体例

`review/review-model.json` は10個の処理比較、71個のレコード項目、37個の制御変数、6個のファイルI/Fを収録する。処理比較の`mappingIds`と項目の`behaviorIds`は相互参照。`oldRanges`／`newRanges`は原本とJavaの使用箇所で、COPY句の抽出定義は`definition`に分ける。

`kind`は対応・差分の種類、`disposition`は採否。現在は全て`unreviewed`で、COBOL実行との直接比較は`not-run`。原本側に同じ検査がないJava追加処理や、個別保持しない項目は、空の根拠範囲と説明で表し、架空の1対1対応を作らない。

この台帳はサンプルの範囲に限定され、全プログラムの制御フロー、DBスキーマ、全依存、実機ログを収録した完全な中間表現ではない。対象を広げる場合は契約の不足項目を補い、既存の成功記録をそのまま流用しない。
