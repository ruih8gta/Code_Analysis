# 変数・データ項目の対応

旧と新で同じ情報が同じ意味で扱われるかを確認する。名前が似ていることは候補の根拠に留め、代入元、検索キー、利用先、型、制約で対応を確かめる。この工程の成果物は対応案と根拠であり、DBの実データ変更やスキーマ変更を自動的に含めない。

## 入力と引継ぎ

旧新の宣言、COPY句、DDL、SQL、ORM／DTO、I/F定義と処理対応を確認する。[共通のレビュー契約](../cobol-java-flow-viewer/references/review-contract.md)の版とIDを使う。存在しないDBテーブルや列を推測で作らない。VSAM／固定長ファイルの対応はその種別を明示する。

## 対応付け

1. 原本と新実装の項目を棚卸しする。変数、レコードのフィールド、ファイル／テーブル、キーと制約を区別する。FILLER、同名項目、REDEFINES、OCCURSは修飾名・位置・繰返し範囲を含むIDで識別する。
2. 名前だけでなく、読込元→変換→代入→検索／更新／出力のデータの流れを辿る。対応関係を1対1に固定せず、分割・結合・集約・計算・定数・廃止・新規・不明を表現する。
3. 型、桁、精度、小数、丸め、符号、文字コード、NULLと空白・ゼロ、初期値、日時、タイムゾーン、キー重複、比較順序を対象に応じて確認する。IDの先頭ゼロやCOBOLのCOMP／COMP-3などの格納表現を、表示文字数と混同しない。
4. 未使用と未移植を区別する。バッチがファイルを開閉するだけなら、すべての項目にJava変数があると装わない。レコードを丸ごと保持する場合も、個別の型変換を確認済みにしない。対象外・廃止には根拠と影響範囲を残す。
5. 対応する旧新の定義と使用箇所、変換規則、具体例、境界・欠損値の確認結果、関連する処理IDを記録する。定義の全文が未取得なら、抽出値のスナップショットと区別する。
6. 変換を実装・検証できる範囲では、境界値や欠損値を使い、桁落ち、丸め、空白、符号、NULL、キー衝突の結果を比較する。例示データの表示だけを変換試験と数えない。

## 画面と確認基準

主画面は項目対応の一覧、選択した項目の旧／新の定義・利用箇所、変換の詳細にする。検索と、未整理・追加・廃止などの絞り込みを用意する。処理比較へ戻るリンクを維持する。

旧側と新側の両方で、対応あり・理由付き対象外・新規・未整理を数える。対応案、実行で確認した変換、業務上の採否を別に記録する。対応数だけで、データ移行の完全性や処理の同等性を判断しない。

成果物は項目対応台帳、データの流れ、変換規則、未整理／差分一覧と確認結果。DBであればテーブル・列・型・キー／制約を含め、ソースレビューとデータ移行実施の範囲を明示する。
