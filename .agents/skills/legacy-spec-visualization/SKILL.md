# 現行仕様の可視化

移行の比較基準となる「現行が実際に行う処理」を作る。主画面は現行ソースと現行フローに集中させる。この工程だけの依頼なら、新コードの生成を作業に含めない。

## 入力と引継ぎ

原本の版・ファイル・文字コードを固定し、取得元とハッシュを記録する。COPY、呼出先、JCL、SQL／DDLなど、意味の確定に必要な依存を列挙する。取得できたものと未取得のものを区別する。

工程間で成果物を渡すときは、[共通のレビュー契約](../cobol-java-flow-viewer/references/review-contract.md)を使う。現行だけを調べる場合も、処理ID・ソース根拠・対応状態・未確認事項を残す。IDを画面の表示順や行番号だけに依存させない。

## 作成手順

1. コメントの目的説明を実装と突き合わせ、対象範囲を決める。エントリ、段落／関数、実行文、条件、ループ、呼出し・復帰、I/O、終了経路を棚卸しする。
2. ソースに対応する構文解析器を使える場合は、その解析結果から制御フローを作る。簡易抽出を使う場合は対象構文と未対応構文を明記し、候補の棚卸しを完全な解析と呼ばない。解析に失敗した文を分母から消さない。
3. 図を業務上の処理単位にまとめ、その配下に文・条件・呼出先の対応を保持する。大きな行範囲を囲うだけで、含まれる全処理を説明できたとは判断しない。
4. 正常だけでなく、条件の両側、分岐なしの合流、ループの継続／終了、呼出しからの復帰、EOF、I/O失敗、未登録、終了処理を点検する。COBOLでは暗黙スコープ、段落のfall-through、PERFORMの範囲、READ INTO後の領域保持にも注意する。
5. 原本の先頭から末尾まで行順に確認できる一覧を作る。実行部に加え、コメント・空行・宣言・定義も残し、フロー対応が不要な理由を表示する。分類不能な行は未解析として残す。対象ファイル全行と、処理フローの点検対象の分母を区別し、COPY展開や別ファイルを含むかを明記する。
6. 一覧の各範囲に「フロー」「条件」「入出力・定義」の対応先と未登録を示す。条件は判定自身と外側のIF・反復条件、真偽側を区別する。入出力は実際の参照名を根拠に結び、原本に疑わしい参照があっても正しい名前へ黙って置き換えない。
7. 図と根拠コードを双方向に移動でき、一覧の範囲から対応先を開いた後も元の行へ戻れるようにする。先頭・末尾、行番号指定、前後、未対応箇所への移動を用意する。複数候補は候補を表示する。図の要約に似た処理があるだけでは、その行の登録済みリンクとして扱わない。閲覧や移動によって網羅率を増やさない。
8. 入出力の定義や条件の詳細は必要時に開く。移行先の型やJavaのコードは次工程の画面に置く。例示経路には入力条件と再構成モデル／実行トレースの別を示す。

網羅性の点検では、原本コードと対応先を同じ行に置く一覧を基本にする。コード全文と、その短い抜粋の一覧を並べて読む幅を圧迫しない。フローや詳細を開いたときにコードとの比較表示へ切り替え、元の行へ戻れるようにする。文字を縮めて列を押し込まず、狭い画面では対応先をコードの下へ移す。説明や数え方は必要時に開き、主画面の大半をコードの確認に使う。

## 確認基準

- 原本の全対象単位が、図への対応・対象外とその理由・未解析のいずれかに分類されている。対象外は理由をレビューできるよう残す。
- 行順一覧が1行目から最終行までを重複・欠落なく含むことと、分類・参照先の妥当性を別々に検証する。代表的な未登録行、外側の条件を持つ行、定義行で、コード選択と対応先への往復を実際に操作する。
- ソース参照が版・ファイル・実在行と一致し、図の辺が条件、呼出し・復帰、ループの構造と整合する。
- 段落、実行文、判定、辺の網羅を別々に集計する。分母を図に登録済みのものだけにしない。
- 構造のレビューと実行による通過計測を分ける。未対応構文や未説明の分岐が残る場合、現行仕様の完全性を保証しない。

成果物は現行フロー、根拠コードへの対応、棚卸しと抜けの一覧、前提／未確認事項。次工程に現行の処理IDを渡す。未確認事項が残っていても、依存しない比較作業は継続できる。

CardDemoの動作例を使うときは[実装メモ](../cobol-java-flow-viewer/references/viewer-implementation.md)を参照する。例の18段落・36判定や固定行番号を他プログラムの基準にしない。
