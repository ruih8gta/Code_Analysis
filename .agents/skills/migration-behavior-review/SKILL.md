# 新旧の処理比較

同じ業務結果になるか、どこが変わったかを確認する。文字列のdiffやコードの似た形だけで同等性を判断しない。既存の移植結果をレビューする依頼では、それを比較対象として保持する。移植も依頼されている場合は、原本を固定し、新コードを作成した後に同じ比較手順を適用する。

## 入力と引継ぎ

原本、新実装、現行処理の棚卸し、入出力契約、実行可能な環境とデータを確認する。「最新」はレビュー時点のコミット／ファイルハッシュで固定する。旧側の版も残す。

[共通のレビュー契約](../cobol-java-flow-viewer/references/review-contract.md)に従い、現行の処理IDと項目IDを引き継ぐ。現行仕様の不足は比較上の不確実性として記録し、独立して調べられる比較を進める。

## 比較手順

1. 旧の処理ごとに、新の処理を対応付ける。1対多、多対1、直接対応なしを表せるようにする。新側だけの処理も逆方向から棚卸しする。
2. 結果・順序・更新先・副作用を確認する。条件式が逆向きでも、業務上の行き先が対応する場合がある。EOF、初期値、境界値、失敗後の継続、検索時点、トランザクション、CLOSE、戻り値、診断出力も対象に含める。
3. 各項目に旧／新の根拠、差分の説明、影響、前提、次の確認、関連するデータ項目を記録する。原本の不具合らしい箇所も差分として残し、勝手に仕様変更が承認された扱いにしない。
4. 実行比較が可能なら、同じ論理入力と初期状態で新旧を実行する。ログだけでなく、終了状態、生成物、DB／ファイル更新、件数、外部I/Fを対象に応じて突合する。日時や順序等を正規化する場合は、その理由とルールを記録する。
5. 旧側を実行できない場合は、原本から導いた期待値との比較や新側の単体検証を行う。その結果を「新旧実行一致」と表示しない。新実装をそのまま期待値にする循環検証にも注意する。
6. ソース、依存定義、入力、比較モデルが変わったら関係する証拠を未検証に戻す。実行日時、環境、入力の識別、期待値の由来、観測結果を残す。

## 画面と状態

主画面は新旧コードと「処理の対応」一覧にする。フロー再生と実行証拠は別の表示へ分ける。一覧から現行フローの根拠と項目対応へ辿れるようにする。

対応の有無、意味上の差分、実行証拠、差分の採否を別の状態として保持する。「対応あり」は「同等性を実証済み」と同義ではない。未決定の差分に承認者や承認日を捏造しない。

成果物は対応台帳、差分／欠落／追加の一覧、実行比較結果、未確認事項、レビュー判断に必要な根拠。完了報告では確認できた範囲を述べ、全入力・全環境での同等性へ一般化しない。
